# Spike S1 — áudio no PipeWire

Pergunta (design §12): `sounddevice` + `pulsectl` funcionam no PipeWire do Nobara para captura,
ducking e mudo do Discord?

**Resposta: sim, com uma dependência de sistema (`portaudio`) e um cuidado com a restauração de volume.**
Script de prova: `spikes/s1_audio.py` (`capture`, `list`, `discord`, `control`, `latency`, `all`).

Ambiente medido (01/10/2026): Nobara (Fedora 44), KDE Plasma 6/Wayland, PipeWire 1.6.8 com
`pipewire-pulse` ("PulseAudio (on PipeWire 1.6.8)", protocolo 35), WirePlumber, sounddevice 0.5.6,
PortAudio 19.7.0, pulsectl via pipewire-pulse. Sink padrão: fone Bluetooth QCY H3 Lite (A2DP);
source padrão: `alsa_input.usb-ME6S_c1_ELITE_08-00.mono-fallback` (headset USB ELITE 08).

## Decisão

| Função | Mecanismo escolhido |
| --- | --- |
| Captura 16 kHz mono, blocos de 80 ms | `sd.InputStream(samplerate=16000, channels=1, dtype="float32", blocksize=1280, callback=...)` no dispositivo `default` (ALSA → `pipewire-alsa`). O PipeWire faz a reamostragem de 48 kHz. |
| Reprodução TTS | `sd.OutputStream` no `default`; abrir por turno é barato (~20 ms). |
| Nome dos nossos fluxos | Variável `PIPEWIRE_ALSA='{ application.name = "magi" media.role = "Assistant" }'` definida antes de abrir o stream. Serve para nos achar no `pulsectl` e para não nos “duckar”. |
| Escolha de microfone | Padrão do sistema; override opcional por `target.object = "<nome do source>"` dentro de `PIPEWIRE_ALSA` (testado). |
| Detectar call / achar o Discord | `pulsectl.Pulse.source_output_list()` filtrado por `application.process.binary` (regra abaixo), não `corked`. |
| Mudo do Discord no PTT | `pulse.source_output_mute(index, True/False)` — mudo por fluxo; o nosso microfone continua ouvindo. |
| Ducking | `pulse.volume_set_all_chans(sink_input, 0.30)`; guardar o `PulseVolumeInfo` original e restaurar com `pulse.sink_input_volume_set(index, original)`. |
| Recuperação após queda | **Obrigatória** para mudo *e* ducking: gravar estado em `$XDG_RUNTIME_DIR/magi/` antes de alterar e restaurar na inicialização (ver Limitações 2). |

Não foi preciso `pw-cli`/`wpctl` nem bindings nativos do PipeWire.

## Resultados

### a) Captura (sounddevice)

- `sounddevice` **não importa** sem a biblioteca do sistema: o wheel Linux não embute PortAudio e o
  pacote `portaudio` **não está instalado** nesta máquina (`OSError: PortAudio library not found`).
  Para o spike, o RPM `portaudio-19.7.0-3.fc44` foi baixado com `dnf download` e extraído no scratchpad,
  usado via `LD_LIBRARY_PATH` (sem root). **Precisa de `sudo dnf install portaudio`** antes da fase 1.
- Host APIs do PortAudio do Fedora: ALSA e JACK (sem host API PulseAudio, que só chega na 19.8).
  `default` (ALSA) passa pelo `pipewire-alsa`; nunca usar `hw:X,Y` (tomaria o dispositivo em exclusivo).
- Resultado com o microfone padrão, 2 s: 25 blocos de exatamente 1280 amostras, intervalo médio entre
  callbacks 82 ms (máx. 86 ms), nenhum overflow, abrir+iniciar 9–16 ms, latência informada 80 ms.
- **RMS = 0,00000 exato** no source padrão (ELITE 08). Confirmado de forma independente com `parec`
  direto no source: silêncio digital também. Logo o pipeline está certo e o problema é do dispositivo
  (botão de mudo do headset, microfone desconectado ou headset errado como padrão). Com
  `target.object` apontando para outro source a captura trouxe sinal (RMS 0,41 / 0,00005), provando que o
  caminho funciona e que a escolha de source por `PIPEWIRE_ALSA` funciona.
- Nada foi gravado em disco; só RMS em memória.

### b) pulsectl contra pipewire-pulse

Funciona sem configuração. `server_info()`, `source_output_list()`, `sink_input_list()` e `proplist`
completos. Propriedades úteis observadas:

| Fluxo observado | `application.name` | `application.process.binary` | Outros |
| --- | --- | --- | --- |
| Jogo Control (Proton) | `' '` (vazio) | `wine64-preloader` | `media.name='audio stream #1'`; `/proc/<pid>/comm = Control_DX12.ex`; `SteamAppId=870780` no environ |
| speech-dispatcher | `speech-dispatcher-dummy` | `sd_dummy` | some após 5 s ocioso |
| Nosso fluxo (ALSA) | `magi-s1` (via `PIPEWIRE_ALSA`) | — | `node.name='alsa_playback.python3.12'`, sem `application.process.id` |

Observação: fluxos vêm e vão (o `sd_dummy` sumiu entre listar e testar); todo acesso por índice deve
tratar `pulsectl.PulseIndexError`.

### c) Discord, Spotify e jogo — como identificar

O Discord não estava aberto. Instalação: RPM `discord-1.0.158` (Nobara); o executável real é
`~/.config/discord/app-1.0.159/Discord`, então `application.process.binary = "Discord"`.
O histórico do WirePlumber (`~/.local/state/wireplumber/stream-properties`) mostra os nomes que esse
Discord já usou nesta máquina:

- `Input/Audio:application.name:WEBRTC VoiceEngine` (mono) — captura de voz da call;
- `Output/Audio:application.name:WEBRTC VoiceEngine` — áudio da call (não deve sofrer ducking);
- `Input/Audio:application.name:discord_capture` (estéreo) — provavelmente captura de áudio de
  compartilhamento de tela; não deve sozinho indicar call.
- Spotify (flatpak): `Output/Audio:application.name:spotify`, com volume 0,40 salvo pelo usuário.

Regras implementadas em `classify()`:

- **Discord (call ativa):** `source-output` com `application.process.binary` contendo `Discord`
  (ou `vesktop`/`webcord`) ou `application.name` `WEBRTC VoiceEngine`, e não `corked`. Discord flatpak:
  conferir também `pipewire.access.portal.app_id = com.discordapp.Discord`. Mutar **todos** os
  source-outputs do Discord encontrados (inclui `discord_capture`, inofensivo).
- **Spotify:** `sink-input` com `application.name`/`binary` contendo `spotify` (esperado
  `pipewire.access.portal.app_id = com.spotify.Client`, a confirmar).
- **Jogo atual:** `sink-input` cujo processo (`application.process.id`) tem `SteamAppId` em
  `/proc/<pid>/environ` (mesmo usuário, legível), ou `binary` em {`wine64-preloader`, `wine-preloader`,
  `wine64`, `wine`}. `application.name` de jogos Wine é inútil (`' '`).

### d) Mudo e ducking

Testado em fluxos próprios (silêncio), sem tocar em apps do usuário — no momento do teste não havia
sink-input de terceiro estável (o do jogo tinha fechado; o do speech-dispatcher sumiu por ociosidade).

- `source_output_mute(i, True)`: mute 0 → 1; com a captura apontada para um source com sinal, o RMS
  que o app recebe foi de **0,41 → 0,000000** mutado e voltou ao desmutar. Mudo é por fluxo.
- `volume_set_all_chans(si, 0.30)`: 1,0 → 0,30 em ~1 ms (round-trip de leitura incluído depois);
  restauração com o `PulseVolumeInfo` salvo volta a 1,0 exato (preserva volumes por canal).
- Tudo em `try/finally`; estado final verificado: nada mutado, volumes originais.
- `--sink-input N` testa o ducking num fluxo de terceiro (com restauração).

### e) Latência de reprodução

`sd.OutputStream` 48 kHz mono: abrir 15–22 ms, primeiro callback 26–32 ms, latência informada 35 ms
(padrão `high`); `latency="low"` informa 9 ms. Isso **não inclui** a latência do Bluetooth A2DP do fone
(tipicamente 150–250 ms, não medida). Abrir um stream por turno é aceitável.

## Limitações e cuidados

1. **PortAudio de sistema** é dependência de runtime: `sudo dnf install portaudio` (documentar no
   instalador/README da fase 1). O PortAudio imprime vários `ALSA lib ...` no stderr ao enumerar
   dispositivos — ruído inofensivo, filtrar nos logs.
2. **O WirePlumber persiste volume e mudo por `application.name`** (`restore-stream`). Testado: fechar um
   fluxo com volume 0,30 sem restaurar faz o próximo fluxo do mesmo app abrir em 0,30. Se o satélite cair
   durante o ducking, o Spotify (ou **todos** os jogos Wine, que compartilham o nome `' '`) ficariam a
   30% para sempre; o mesmo vale para o mudo do Discord. Por isso o satélite deve gravar, antes de
   alterar, `{application.name, índice, volume original}` em `$XDG_RUNTIME_DIR/magi/` e restaurar na
   inicialização — estender o `discord-muted` do §3.2 para o ducking também. Se o fluxo original já
   tiver sumido, o valor errado fica salvo no WirePlumber; a correção é aplicar o volume original ao
   próximo fluxo daquele `application.name` assim que ele aparecer (o WirePlumber então salva o valor certo).
3. Um sink-input pode aparecer/desaparecer a qualquer momento (pausa do Spotify, troca de fase do
   jogo): reaplicar o ducking em fluxos novos durante a fala e tratar `PulseIndexError`.
4. Nossos próprios fluxos não têm `application.process.id` (vêm pelo `pipewire-alsa`), por isso a
   identificação é pelo `application.name` definido em `PIPEWIRE_ALSA`.
5. Os testes deixaram entradas inofensivas (volume 1,0, sem mudo) `magi-s1*` em
   `~/.local/state/wireplumber/stream-properties`; podem ser apagadas com o WirePlumber parado, se quiser.
6. Detecção do Discord e regras de Spotify/jogo não foram exercitadas ao vivo (apps fechados).

## Teste manual pelo usuário

Com `sudo dnf install portaudio` feito (ou o `LD_LIBRARY_PATH` do spike):

1. **Microfone:** verificar o botão de mudo do headset ELITE 08 (ou definir o microfone certo como
   padrão no KDE), falar e rodar `uv run python spikes/s1_audio.py capture` — RMS médio deve passar de
   ~0,01 ao falar.
2. **Discord:** entrar numa call e rodar `uv run python spikes/s1_audio.py discord --mute-test`. Esperado:
   source-output `[discord]` com `binary='Discord'`; durante 0,5 s os outros da call não ouvem; depois
   volta. Anotar `application.name`, `media.name` e se há `discord_capture`.
3. **Spotify:** tocar música, rodar `uv run python spikes/s1_audio.py list`, anotar o índice `[spotify]`
   e rodar `uv run python spikes/s1_audio.py control --sink-input <índice>` (volume cai a 30% por 0,5 s e
   volta). Confirmar `pipewire.access.portal.app_id`.
4. **Jogo:** com um jogo Steam rodando, `list` deve marcá-lo `[game]`; repetir o passo 3 com o índice dele.
